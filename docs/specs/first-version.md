# First usable version: STEP part review

- **Status:** Approved 2026-11-06 ([spec approval](https://claude.ai/artifact/CAqfoCYn9pSSxkBHn4peGb))
- **Planned in:** [design round 1](https://claude.ai/artifact/4Xa6iLguwU2pnXQXCAYydk), [round 2](https://claude.ai/artifact/LEGMPWU3Avt4E9pjnSvbhG), [approval](https://claude.ai/artifact/WDr91uJChvS9RkBziPWDHo) (2026-11-06). **Decisions:** D-001, D-003, D-004, D-005, D-006, D-007, D-008, D-010 to D-015.

## Problem

Design reviews for manufacturability are "not really done at all" today (Morgan). The tool "should improve the designs of parts and improve manufacturing efficiency": a design companion for design mechanical engineers and shop managers. Morgan's test for the first deliverable is a "report with findings and machine estimates". In this version, machine estimates means the machine type, the setups, the tools and the tool changes; time comes later (D-003). Morgan "would hate if it was not useful", so every finding must show its evidence.

## Goals

- Morgan uploads one STEP part, picks milling or turning and a material, and gets a review in the browser. Every test part finishes in under 10 s (measured by `test_runtime`).
- Each finding shows its measured value, the limit it broke and its faces highlighted in 3D.
- The review names the machine type and lists the setups, the generic tools and the tool changes. It ranks what drives cost, with no time and no dollars (D-003).
- All 7 rules pass their test parts: hole depth vs diameter, non-standard hole size, inside corner radius, deep pocket, thin wall, access and setups, and turning checks. Turning checks are two modules, `turn_slender` and `turn_offaxis`. Each rule has at least 2 flagged test parts plus 1 clean part (D-005).
- The review exports as a PDF with one image per finding.
- Every machine builds from one environment file with no Docker. The app starts with one command at `http://localhost:8000` (D-004).

## Non-goals

- These come in later phases (D-003):
  - assemblies and DFA
  - saved history and revision compare
  - time and dollars
  - accounts and batch upload
  - Morgan's own machine and tool lists
  - native Inventor files
  - number and letter drill sizes
- Exterior profiles, steps, open-sided pockets, threads, floor fillets and thin cylindrical shells (tubes, sleeves) are not planned or ruled on in this version. They are listed in `assumptions`.
- Faces other than planes, cylinders, cones, and the cylinder or torus fillets between pocket walls. The tool lists any other face in `not_analysed_faces` instead of guessing.
- Choosing milling or turning automatically. The user picks; the tool warns when turning is picked and no turning axis is found, and (D-028) when milling is picked for a part that looks turned.
- Any AI at runtime (D-001).
- The drawing check and drawing generation (stages 3 and 4).

## Decisions

- One part per upload. The user picks milling or turning, and one of 4 material groups (D-003).
- Geometry runs in a Python service on OpenCascade 8.0.1 (pythonocc-core 8.0.1.2). The web page is TypeScript with three.js, and the PDF is built in the browser with jsPDF (D-004).
- One conda `environment.yml` serves every machine, with no Docker. The app serves at 127.0.0.1:8000 (D-004).
- Face ids are assigned when a file is read, and the mesh and every finding carry them. Thresholds are set per material in `config/thresholds.toml`, each labelled with its source or `estimate`. Lengths are millimetres inside and inches on screen (D-005).
- Cost drivers are shown with their counts and weights and ranked by count × weight, with no time or dollars (D-003).

## Alternatives rejected

- **Rust or C++ around OpenCascade:** same engine, slower development. There is no Rust STEP reader, and the Rust wrapper is "a major work in progress". It would fail when the wrapper's coverage runs out (D-004).
- **OpenCascade in the browser (WebAssembly):** runs the older version 7.6.2 and is limited by the browser tab's memory. It would fail on large or messy files (D-004).
- **Docker:** Morgan expects IT to refuse it, and the work copy is rebuilt through GitLab (D-004).
- **Automatic process detection:** misreads a milled part with a large bore, or a shaft with flats. It would fail on any part that mixes both processes.
- **Machine-learning feature recognition:** needs training data, gives no measurable evidence, and Morgan wants no AI (D-001).
- **Browser print-to-PDF with print CSS:** needs no library and gives selectable text. jsPDF wins because it is a single click with no dialog, and its text is selectable too. Print would fail Morgan's "Export PDF" one-tap flow on phones and some browsers.
- **Headless browser on the server for PDF images:** the user's browser already renders the view. That would only matter if a PDF had to be made with no browser open, which isn't a goal.
- **glTF for the mesh:** plain JSON with per-face arrays keeps face ids obvious. JSON would become too slow on parts above about 200,000 triangles (assumption), and glTF should be revisited then.
- **File axes for setups:** a part modelled at an angle would get every feature flagged. The part frame comes from its own faces instead (see Design).

## Risks

- **OpenCascade misreads real STEP exports, or loses AP242 data.** S1 reads public files once their licence is checked, and Morgan can upload a real part from S2 (open question 1).
- **Feature recognition misfires on real parts** (split hole faces, blended fillets). Mitigation: analytic faces only, `not_analysed_faces` for the rest, and test parts that include split cylinders, stepped holes and drill-point bottoms.
- **Thresholds are wrong.** Each one is an editable, labelled estimate, and every finding shows the limit it used.
- **The Windows setup differs from the Linux cloud build.** J1 runs on Morgan's PC as S1's device check. Paths use `pathlib`, and there are no shell scripts.
- **Headless WebGL in CI is flaky.** S1 proves it with the canvas check before any PDF work.
- **Scope creep.** The non-goals hold the line; anything new goes to HANDOFF as a later phase.

## Design

### Layout

- `environment.yml` (conda-forge only):
  - pins `python=3.12`, `pythonocc-core=8.0.1.2` and `nodejs=22`
  - pins `fastapi`, `uvicorn`, `python-multipart`, `pytest`, `httpx`, `playwright`, `pytest-playwright` and `pypdf`
  - installs the service with a pip entry, `-e ./service`
  - S1 resolves each package to an exact version and writes it in
- `service/pyproject.toml` and the package `service/dfma/`:
  - `__main__.py`: the `start` command.
  - `app.py`: the FastAPI routes.
  - `analyze.py`: `analyze(path, name, process="mill", material="al6061")` runs everything below in the current process and returns the response dict; `name` is the uploaded file name. It raises `ReadError(message)` for J7 inputs.
  - `worker.py`: `run_analysis(path, name, process, material, time_limit_s=60)` sends the job to the warm worker, enforces the limit and raises `AnalysisTimeout`. `app.py` calls only `run_analysis` and maps both errors to 422. Until a slice adds them, `features`, `findings`, `setups`, `operations`, `tools` and `cost_drivers` are empty lists, `machine` is null and `tool_changes` is 0.
  - `read.py`, `frame.py`, `mesh.py`, `features.py`, `tools.py`, `plan.py`, `turning.py`, `drivers.py`, `settings.py`, `units.py`.
  - `rules/`: one module per rule.
- `config/thresholds.toml`, `config/tools.toml`, `config/drivers.toml`: editable settings, described below.
- `web/`:
  - Vite + TypeScript + three.js + jsPDF, with `package.json` and `package-lock.json` exact-pinned in S1
  - source files `src/main.ts`, `src/viewer.ts`, `src/findings.ts`, `src/report.ts` and `src/api.ts`
  - `npm run check` runs `tsc --noEmit` and `vitest run`; S1 adds `web/src/format.test.ts` (inch and fraction formatting)
  - test hooks: `data-testid` on `upload-file`, `upload-process`, `upload-material`, `viewer-canvas`, `part-size`, `face-count`, `error-message`, `finding-<id>` and `export-pdf`; `window.__dfma.highlightedFaces(): number[]` and `window.__dfma.cameraTarget(): [x, y, z]` (mm, file coordinates). "Frames the faces" means the camera target is within 1 mm of the centre of those faces' bounding box.
- `tests/parts/make_parts.py`: builds every test part with OpenCascade and writes the STEP files and `expected.toml` (with a small string writer in the script, no TOML library; reading uses the standard `tomllib`). Both are committed.
- `tests/service/` and `tests/e2e/`: pytest, with e2e tests marked `e2e` and run through Playwright for Python. A root `pytest.ini` registers the marker. `pytest-playwright` (pinned in `environment.yml`) gives the `page` fixture; `tests/e2e/conftest.py` starts the app with `python -m dfma start --no-build --port 8765` against a prebuilt `web/dist`. Browsers are installed once with `python -m playwright install chromium`, written in the README and in CI. The cloud session uses its preinstalled Chromium.
- `scripts/check.py`: runs every local check in order and stops at the first failure. Cross-platform, Python only.

### Start

`python -m dfma start [--no-build] [--port 8000]` does three things:
1. It runs `npm ci` and `npm run build` in `web/` when `web/dist` is missing, unless `--no-build` is given.
2. It serves `web/dist` and the API with uvicorn on 127.0.0.1 at the given port (default 8000).
3. It prints the URL.

### Flow

1. The browser posts `multipart/form-data` to `POST /api/analyze` with three fields:
   - `file`
   - `process`: `mill` or `turn`, default `mill`
   - `material`: `al6061`, `steel1018`, `ss304` or `plastic`, default `al6061`. In the UI, `steel1018` is labelled "Steel 1018/1045", `ss304` "Stainless 304/316" and `plastic` "Delrin / nylon".
   The upload panel has all three fields from S1 onwards.
2. Uploads with a `Content-Length` over 50 MB get a 413 before the body is read, and the body stream is cut off at 50 MB in case the header is missing or wrong. Otherwise the bytes go to a temporary file created with `tempfile.NamedTemporaryFile(suffix=".step", delete=False)`, which is removed in a `finally` block after the analysis. Nothing is kept (APP-01). The reader needs a file path, so this is an assumption about the pythonocc API: no stream read is used.
3. `analyze()` runs in one long-lived worker process, started at launch with the `spawn` method so that pythonocc is imported once. It returns plain dicts only. If the time limit passes, the worker is terminated and a new one is started, and the API answers 422 with the J7 message. S1 measures the time from upload to response on Morgan's PC.
4. Reading uses `STEPControl_Reader`:
   - Status not done means "This is not a STEP file this tool can read".
   - No solid means "No solid found in this file".
   - With several solids, it keeps the largest by volume and counts the rest in `ignored_solids`.
   - It reads the length unit, converts to mm and gives face ids from 0 in `TopExp.MapShapes(shape, TopAbs_FACE)` order. Ids hold within one analysis only.
5. `frame.py` sets the part frame:
   - +Z is the outward normal of the largest-area planar face (areas within 0.1% tie; ties go to the lowest face id).
   - +X is the outward normal of the largest planar face perpendicular to Z, within 0.5° (same tie rule).
   - Y is Z × X.
   - With no planar faces, Z is the axis carrying the most cylinder and cone area, pointing towards the end with more face area at its extreme. `turn_axis` uses the same sign rule.
   - With no planar face perpendicular to Z, +X is the file X axis projected onto the plane normal to Z, or the file Y axis if file X is within 10° of Z.
   - `bbox_in` holds the extents along frame X, Y and Z, measured by projecting the mesh vertices; the screen shows them largest first.
   - `faces.positions` are in file coordinates, mm.
   - All directions below (±X ±Y ±Z) are in this frame.
6. `mesh.py` triangulates with `BRepMesh_IncrementalMesh` (linear deflection 0.05 mm, angular deflection 0.5 rad; assumption). The renderer keeps `preserveDrawingBuffer: true` from S1 onwards.
7. The analysis then runs in order:
   - `features.py`
   - `rules/*`
   - `plan.py` (mill) or `turning.py` (turn)
   - `drivers.py`
   The rule modules shared by both processes are `hole_depth`, `hole_size` and `thin_wall`. `corner_radius`, `pocket_depth` and `access` run for mill only. `turn_slender` and `turn_offaxis` run for turn only.

### Response schema (`POST /api/analyze`, 200)

```
{
  "part":     { "name": str, "units_in_file": "mm"|"cm"|"m"|"inch"|"none"|"other", "bbox_in": [x,y,z],
                "face_count": int, "volume_mm3": float, "ignored_solids": int,
                "not_analysed_faces": [int], "frame": {"x":[3], "y":[3], "z":[3]} },
  "faces":    [ { "id": int, "kind": "plane"|"cylinder"|"cone"|"torus"|"other",
                  "positions": [float], "indices": [int] } ],
  "features": [ { "id": "hole-1"|"pocket-1"|"corner-1"|"wall-1"|"groove-1"|"bore-1"|"profile-1",
                  "kind": str, "faces": [int], "axis": [x,y,z] | null,
                  "open_dirs": ["+Z", ...], "open_vectors": [[x,y,z], ...], "dims_mm": {name: float} } ],
  "findings": [ { "id": "F1", "rule": str, "severity": "high"|"medium"|"low",
                  "title": str, "measured": float, "limit": float, "unit": "in"|"ratio"|"deg"|"%",
                  "faces": [int], "feature": str, "threshold_source": str, "suggestion": str } ],
  "machine":  "3-axis mill"|"4/5-axis mill or fixture"|"lathe"|"lathe with live tooling"|null,
  "turn_axis": [x,y,z] | null,
  "setups":   [ { "direction": "+X"|"-X"|"+Y"|"-Y"|"+Z"|"-Z"|"turn", "features": [str] } ],
  "operations": [ { "setup": int /* 0-based index into setups */, "tool": str, "features": [str] } ],
  "tools":    [ { "id": "dr-0.2500"|"em-0.250"|"turn"|"bore"|"groove-0.125", "kind": str,
                  "diameter_in": float | null, "undersized": bool } ],
  "tool_changes": int,
  "cost_drivers": [ { "driver": str, "count": int, "weight": float, "score": float } ],

```

- Feature ids number from 1 per kind, in face-id order. Finding ids number from F1, in the rule order of the Rules section and then feature order.
- Errors return 413 or 422 with `{"error": str}`.
- `"low"` severity is in the schema for later rules; no rule in this version produces it.

### Features (analytic faces only)

- **Hole:** connected concave cylindrical faces (sharing edges) with the same axis (within 0.5°) and radius (within 0.001 mm). Split half-cylinders merge into one hole; two same-size holes with material between them stay two holes. After merging, the faces must span the full 360°, so a pocket-corner fillet is never a hole.
  - An end is open when its circular edge borders a face that isn't part of the same hole chain (an outer face or a pocket face). Its direction is the axis pointing out of the material at that end, also on a pocket face (D-022 dropped "an end on a pocket face takes the pocket's open direction").
  - `open_vectors` lists every open end's direction; `open_dirs` lists those that match ±X ±Y ±Z of the frame within 0.5°. The segments of a stepped hole are one chain, and every segment takes the chain's open ends.
  - Depth of a stepped segment is its own length along the axis.
  - A stepped hole is one hole feature per diameter segment. Each segment carries `chain`, a number shared by the segments of one stepped hole (added 2026-11-07 for the hole-joins set, D-018).
  - A cone bottom (drill point) is part of the hole. Its depth is measured to where the cone starts, and the cone is recorded in `dims_mm.point_mm`.
  - `open_dirs` holds every end that opens onto an outer face, so a through hole has two.
- **Pocket:**
  - The floor is a planar face. Its walls are the concave neighbours perpendicular to it (within 0.5°), and they must close a loop.
  - A loop made only of cylindrical faces with one radius is a hole (flat-bottom hole or counterbore), not a pocket.
  - Island walls, which are convex towards the floor, are allowed.
  - Depth runs from the floor to the highest wall edge.
  - `open_dirs` is the floor normal.
  - Open-sided pockets are out of scope (see Non-goals).
- **Inside corner:** the concave edge, or the cylinder or torus fillet, between two adjacent pocket walls. Its radius is the fillet radius, or 0 for a sharp edge.
- **Wall:** two parallel planar faces whose outward normals point away from each other, with solid material between them. Added by D-020: faces up to 15 deg from parallel (draft) count too, with the thickness at the thinnest place; faces that meet (a knife edge) are no wall. ~~The midpoint of the shortest segment between the two faces is classified IN by `BRepClass3d_SolidClassifier`.~~ Changed in S4: for parallel faces that segment ends on an edge, so its midpoint is ON, not IN, and a plain block had no walls. Instead:
  - Only pairs with opposed normals (within 0.5°) whose bounding boxes overlap once one face is moved onto the other's plane are measured, to keep the search short.
  - Their overlap (`BRepAlgoAPI_Common` of the moved face and the other face) is at least 10 mm² (assumption).
  - Material between: a ray from a point inside the overlap, into the material, meets the other face first. The points tried are the centroids of the overlap's mesh triangles, then a 9 × 9 grid on it; one clear ray is enough.
  The thickness is the distance between their planes. A slot's two sides face each other, so they are never a pair; two bosses facing away with air between fail the ray test.
  - **At holes (D-016):** per hole, the thinnest material around its side (rays square to the axis from 3 heights of its round part, every 15° then every 1° near the nearest) and, for a drill point, under its tip (rays from the tip up to 30° off the axis, deeper into the part). Rays start only on the hole's face itself (not where a cross hole cuts it). The first face a ray meets bounds solid material. Measured up to 0.250 in (assumption); two holes that find each other give one wall, however their faces are split.
- **Turned profile** (turn only):
  - The axis is the one shared by the most cylinder and cone area.
  - The diameter is the largest outer diameter; the length is the extent along the axis. A thin section behind a large head can read as stocky: this is listed in `assumptions`.
  - If that axis's cylinder and cone area is under 40% of the part's total face area (assumption), rule `turn_axis` gives "No turning axis found; check the process" (high; measured the share in %, limit 40, unit `%`). Then only the shared rules run. `block_as_turn` is the 2 × 1 × 0.5 in block with one 0.250 in hole, uploaded for turning.
- **Groove** (turn only): a cylindrical floor on the axis that is deeper than the cylinders on both sides (smaller radius outside, larger radius in a bore), between two planar faces perpendicular to the axis (external or internal). Its width is the distance between those faces.
- **Bore** (turn only): an on-axis hole of 0.500 in diameter or more. An on-axis hole is either a bore (0.500 in and over) or a hole (under 0.500 in), never both; `hole_depth` applies to it once.

### Tools (`tools.py`, `config/tools.toml`)

- **Drills:** every 1/64 in from 1/64 to 1 in for inch files. For files in mm, metric drills as well (D-013; was "instead"): 1.0 to 13.0 mm in 0.1 mm steps and 13.5 to 25.0 mm in 0.5 mm steps. The set is chosen by `units_in_file`; inch files never get the metric grid, so the 0.1 mm grid can't hide an odd inch size in an inch file. Sizes are generated by rule, not copied from a table.
- **End mills, inch:** 1/32, 1/16, 3/32, 1/8, 3/16, 1/4, 3/8, 1/2, 5/8, 3/4 and 1 in.
- **Turning:** `turn`, `bore` (bores of 0.500 in and over) and `groove-0.125` (grooves of 0.125 in and wider).
- **`pick_end_mill(min_corner_radius, narrowest_width)`:** returns the largest end mill whose radius is at most the corner radius and whose diameter is at most the width.
- **When nothing fits:** for example a sharp corner, it returns the smallest end mill with `undersized: true`.
- **Use:** S2 adds `tools.py` with drills; S3 adds end mills and `pick_end_mill` for `pocket_depth`; S5's `plan.py` and S6's `turning.py` reuse it. `tools.toml` holds the drill ranges and steps, the end-mill list and the turning tools.
- **Hole tools:** a hole with no matching drill gets `pick_end_mill(min_corner_radius=hole radius, narrowest_width=hole diameter)`.
- **Pocket inputs:** `min_corner_radius` is the smallest corner radius in the pocket; `narrowest_width` is the smallest distance between two non-adjacent walls (`BRepExtrema_DistShapeShape`).

### Rules

Limits come from `thresholds.toml` for the chosen material. All starting values are labelled `estimate`.

- **`hole_depth`:** depth ÷ diameter over 6.0 is medium; over 10.0 is high.
- **`hole_size`:** flags a diameter that matches no drill in `tools.toml` within 0.0005 in. Medium. The suggestion gives the nearest drill.
- **`corner_radius`:**
  - One finding per corner, at the worst severity that applies; its title names every reason.
  - A sharp corner (radius 0) is high: "needs EDM or a corner radius", measured 0 in, limit 0.0313 in.
  - A radius under 0.0313 in (1/32 in) is medium.
  - If the radius is over 0 and depth ÷ the diameter of the end mill `pick_end_mill` returns is over 4.0, that is also a medium reason: the tool that fits is long and thin.
- **`pocket_depth`:** pocket depth ÷ the diameter from `pick_end_mill` is over 3.0. Medium. An undersized pick adds "smallest tool used" to the suggestion.
- **`undercut`** (added by D-021, mill only): a pocket with an undercut (a ceiling facing its floor, D-018 set 2). Measured: how far the undercut reaches under its lip, in inches; limit 0. Medium: "needs a T-slot or lollipop cutter".
- **`thin_wall`:** thickness under 0.030 in (`al6061`), 0.020 in (`steel1018`, `ss304`) or 0.060 in (`plastic`). High.
- **`access`:** a hole or pocket with no `open_dirs` along ±X ±Y ±Z of the part frame (within 0.5°). Measured: the angle in degrees between its nearest open vector and the nearest frame axis; limit 0.5; unit `deg`. High: "needs a 4/5-axis mill or a fixture". It sets `machine` to "4/5-axis mill or fixture".
- **`turn_slender`:** length ÷ the smallest outside diameter (D-026) over 4.0 is medium (over 3.0 for `steel1018` and `ss304`, D-025); over 8.0 is high. The suggestion names the support (D-026).
- **`bore_depth`** (D-026, turn only): a bore's depth ÷ diameter over 4.0 is medium (carbide bar), over 6.0 is high (damped bar).
- **`turn_offaxis`:** flags a hole or pocket whose axis is not coaxial with the turning axis. Coaxial means within 0.5°, with an offset of 0.001 in or less. Medium: "needs a milling operation or live tooling". It sets `machine` to "lathe with live tooling".

### Plan (`plan.py`, mill)

1. **Setups:**
   - Each hole or pocket can be machined from any direction in its `open_dirs`.
   - The setups are the smallest set of directions covering every feature that the `access` rule didn't flag. They are found by brute force over the 63 non-empty subsets of ±X ±Y ±Z.
   - Ties go to the subset whose directions come first in the order +Z −Z +X −X +Y −Y, compared position by position.
   - Each feature is assigned to the first setup in that order that covers it.
2. **Machine:** "3-axis mill", unless `access` flagged a feature.
3. **Operations:**
   - One operation per (setup, tool), with setups in that same order.
   - Within a setup: end mills from largest to smallest, then drills from smallest to largest.
   - Holes take the matching drill, or `pick_end_mill` when no drill matches. Pockets take `pick_end_mill`, after a roughing end mill when one larger fits (D-029).
4. **Tool changes:** the number of operations. Every tool load counts, including the first in each setup; the screen calls it "Tool loads (including the first in each setup)". This counting rule is listed in `assumptions`.
5. **At least one setup:** a part with no holes or pockets still gets 1 setup (+Z).
6. **Exterior faces:** not planned in this version. This is listed in `assumptions`.

### Turning (`turning.py`)

1. **Setup:** one setup, `turn`.
2. **Operations, in order:**
   - `turn`
   - an on-axis hole drill, the matching drill
   - `bore` for each bore of 0.500 in or over
   - `groove-0.125` for each groove
   - each off-axis feature as a milling operation with `pick_end_mill` or a drill
3. **Machine:** "lathe", or "lathe with live tooling" if `turn_offaxis` fired.

### Cost drivers

- **Drivers:**
  - setups beyond 1
  - distinct tools
  - undersized or sub-1/8 in tools
  - deep holes
  - non-standard holes
  - thin walls
  - sharp or small inside corners
  - off-axis features
  - features needing 4/5-axis
- **Scoring:** each driver's score is its count × its weight from `drivers.toml`. The starting weights are labelled `estimate`.
- **Counts:** `extra_setups` is setups − 1; `distinct_tools` is the number of tools; every other driver counts its findings (or, for `small_tools`, tools marked `undersized` or under 1/8 in across; D-030). Every starting weight is 1.0 (`estimate`).
- **Display:** the response and the report hold only drivers with a count above 0, with their label, count, weight and score, sorted by score (high first) and then by key (A to Z). Driver names are the bullets above, in `drivers.toml` keys `extra_setups`, `distinct_tools`, `small_tools`, `deep_holes`, `odd_holes`, `thin_walls`, `small_corners`, `off_axis`, `multi_axis`, plus D-030's `deep_pockets`, `undercuts` and `slender_parts`. A feature can count under more than one driver, because each driver is a separate cost.

### Units

- Lengths are millimetres inside and inches on screen to 0.001 in.
- A value within 0.0005 in of a 1/64 in multiple also shows as a fraction, for example "0.250 in (1/4)".
- Ratios show to 0.1.
